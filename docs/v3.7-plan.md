## 3.7a: the spike

Questions, each answered with the cheapest proof (a no-login probe first, one tiny real run only if nothing else can):

1. Can `plugin/agents/lead.md`'s `skills:` line name a skill of another plugin (`woa-team:notes-lead`), and does its
   text reach the model? (A code word in the skill, asked for in one tiny run.)
2. When that skill is missing (no team plugin in a project, or no notes yet), does the Lead still start, and with
   what in the debug log?
3. Does a guild lead started as a subagent get its preloaded skill the same way?

If the answer to 1 or 2 is no, see below.

## 3.7b: proposals

- The five prompts get one line: end a report with at most one `Proposed note: <text>` when something learned in this
  run would help the next one: a fact about the project, never a secret, never a rule or instruction to an agent.
- `send.mjs` already forwards an agent's last message, scrubbed, up to 20,000 characters. The hall reads a proposal from
  the Lead's `Stop` and from a guild lead's `SubagentStop` only, the last line only, and never from a specialist or a
  frame. It is untrusted text: the schema caps it, and the page shows it as text only.
- The feed shows "Note proposed by <name>" as an ordinary row: never a flag, as flags come only from hook types.

## 3.7c: approve, reject, delete

- `POST /api/team` takes `note-approve` (a proposal id), `note-reject` (an id) and `note-delete` (an agent and a note
  id), with the same cookie and Origin rules as every team change. `team.mjs` checks the text again (the skill text's
  refusals: a line starting with `` !` ``, invisible characters), writes `notes.json` in the team folder under its
  strict schema and the caps, and generates the notes skills. A pane line for each ("Note approved for the Lead").

## Where this could stop

- If a plugin agent can't preload the team plugin's skill (3.7a), the ways left are a hook that answers Claude Code
  with text at session start (today only the guard answers, and only with a deny), or writing into the plugin's own
  folder (a copy in Claude Code's cache, which updates would undo). Both loosen a rule, so the build stops there for
  Dima's decision.
- Approved agent text on disk is new: M5 is Dima's decision, and nothing unapproved is ever written.

## Security notes

- A hijacked agent can propose a planted instruction. The gate is Dima's approval: the whole text, cleaned, with links,
  command-like lines and imperative wording toward agents flagged; refused with invisible characters; capped; deletable
  at any time. Notes are loaded under a header that says they are context, not rules, and an agent's limits stay its
  tools and the guard, never its text.
- A proposal counts only from an agent's own final report, by the agent type Claude Code puts in the hook, so a page an
  agent read can't make one appear to come from the Lead. Specialists can't propose.
- Pending proposals live in memory only. Only Dima's actions write the team folder; agents can't (the guard, the
  template).
