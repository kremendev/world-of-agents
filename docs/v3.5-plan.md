## What was checked first (14 Nov, no model run)

**Does a detached hall outlive its session?** A throwaway plugin (`~/Downloads/woa-probe-detach`, deleted after) whose
mod runs a fixed launcher at `session.start`; the launcher starts a child with Node's `detached: true`,
`windowsHide: true` and `stdio: 'ignore'`, unrefs it and exits.

- In the terminal CLI (2.1.319, no login, a temporary config and home): the child outlived `claude.exe`, had no window
  (`MainWindowHandle` 0) and was in no job object. The engine puts no job of its own on `$.process.run`'s children.
- The desktop app is an MSIX package (`C:\Program Files\WindowsApps\Claude_…`): every process it starts, its sessions'
  `claude.exe` and the hall a session started included, is in a job object. Node's detach doesn't leave a job (libuv
  never asks for `CREATE_BREAKAWAY_FROM_JOB`, and a launcher run from a PowerShell in a job left its child in that job).
  So in the desktop app the detached hall lives in the package's job: it outlives the session that started it and any
  reload (the engine kills only what it spawned itself), and may go when the app quits. That is for Dima's test. A way
  out of the job (WMI's `Win32_Process.Create`, a scheduled task) is what security tools flag, so it isn't used; if the
  hall dies with its session in the desktop app, that is a stop for Dima.

**The tooling.** `npm audit`: 7 moderate, all one advisory, `minimatch` >=7.0.0 <11.0.1 (GHSA-g3hv-75wg-m249, a denial
of service through glob patterns), pulled in by `@typescript-eslint/typescript-estree` 8.72.2 (`minimatch ^10.2.2`).
typescript-eslint 8.72.2 is the newest stable and its peer range for TypeScript is `>=4.8.4 <6.1.0`; only its canary
has `minimatch ^11.0.1`. TypeScript's newest is 7.0.2 (the native compiler), ESLint's 10.15.0.

## Security notes

- A detached hall lives longer, so its token file does too: the same token, handshake and checks guard it, and it stops
  itself when idle. It runs nothing and prints nowhere.
- `/api/stop` lets anything that can read the token stop the hall: the same trust as posting hooks, and only for a
  caller that states a newer version. A browser can't reach it (Origin refused, no CORS, no token).
- Kept sessions hold up to three sessions' agent text in memory instead of one, never on disk, gone when the hall stops.

## 3.5b: a hall that stops itself (built 15 Nov)

- `plugin/hooks/hall-start.mjs` (H3) and `plugin/hooks/hall-stop.mjs` (H5), with their `.d.mts`; the mod's `keepHall()`
  runs them (no `process.spawn` for the hall any more, so the voice is the only long-lived child); `stoppable()` and
  `otherHallLine()` (H6). The hall: `POST /api/stop`, the idle stop, `shutdown()` (the token file first, then the port).
- Tests: `server/hall-life.test.ts` (the stop's controls and versions, after its 204, once; idle with a faked clock: a
  hook, a page, a page leaving; the shutdown order; `isNewer()`), `tests/plugin/hall-start-stop.test.ts` (the exact
  spawn options, a real detached run in its own folder, the waits, the stop against real halls, the token never sent
  before the handshake), and the kit's `hall.test.tsx` (the fixed scripts and their order, a later version played
  through `keepHall(…, own)`). Planted bugs: 38, all caught.
- End to end, no model run: a copy of the plugin on port 4329 with a 20 s idle time, started by the real mod in a
  no-login `claude -p` with a temporary config and home. The hall outlived `claude.exe` (no window, no parent, no job),
  stopped itself when idle and deleted its token; an older plugin's stop was refused (exit 5), two starts at once left
  one hall, a newer plugin's stop freed the port and deleted the token.
- Not proven: the desktop app keeps its processes in its package's job, so whether the hall outlives a closed session
  there, and what quitting the app does, is for Dima's checklist.

## 3.5c: each session's activity (built 15 Nov)

- `server/hall.ts`: `heard()` routes each hook. When the hall switches sessions it keeps the one it leaves (its map
  state and its replay); a session it kept comes back as it stood, through `restore()`: `replaying`, a reset if its run
  has none, the run, this hook's events, then `replayed` with the same start id. A `startup` or `clear` for a kept id
  starts it new. A kept session's own hooks run through its own map state and grow its replay, and reach no page.
  `KEPT_SESSIONS` = 3, the oldest dropped first; each run capped at `REPLAY` (500); memory only.
- `src/live/hall.ts`: `replaying` starts a new batch, which `replayed` hands over in one go: the page rebuilds the run,
  hushed (nothing said again), with no "Hall restarted" (same start id).
- Tests: `server/sessions.test.ts` (back by a prompt and by a resume, F5, carrying on after, adopted mid-run, a kept
  session's hooks, the fourth session, a new start, the cap, nothing on disk), `hall.test.ts` (3.4g's switch now shows
  the older run), `src/live/hall.test.ts` and `App.live.test.tsx` (one go, nothing doubled or said again). Planted bugs:
  15, all caught. In Edge, a fresh temporary profile, a real hall on a free port with the built page: A's run and card,
  B's, back to A with its card and the new prompt, no "Hall restarted", the same after F5, no page errors.
