# v3.8.0: template version 4

Dima's brief of 16 Nov, after v3.7.0's release: the two warnings Claude Code 2.1.325 prints in every set-up project.

1. "Plugin "world-of-agents" set this session's agent. That will stop working in a future release: set `agent` in your
   own settings or pass --agent." `plugin/settings.json` was what made the Lead the main agent.
2. "Permission deny rule (.claude\settings.local.json): Write(~/.world-of-agents/**) is not matched by file permission
   checks — only Edit(path) rules are." Template version 3's third team-folder deny.

What he asked: probe the project's `agent` first, in the terminal and the desktop app (with the plugin on, switched off
and uninstalled); then the setup writes `"agent": "world-of-agents:lead"`, `plugin/settings.json` drops it, `woa` passes
`--agent`; drop the `Write(...)` deny, keep `Edit(...)` and `Read(...)`, with the guard as the second layer; the upgrade
from template 3 keeps the user's rules; say whether a user-scope install still makes every session the Lead; stop after
the probe if the desktop app doesn't take the setting.

**A user-scope install no longer makes every session the Lead.** It is still never right: its hooks run in every session
of every project, each reports to the hall, and the guard lets no main thread but the Lead start an agent or edit a file,
so every other project gets a Claude Code that can't edit. The pane's "World of Agents is on for every project." line
stays.

**The desktop app.** I can't drive the app, and the auto-mode check refused unpacking its code (not tried another way).
What it shows from outside, app 5.11492.5 with its own engine 2.1.325:

- Its Code-tab engine runs as `claude.exe --output-format stream-json --verbose --input-format stream-json --model=…
--permission-prompt-tool=stdio --allowedTools=… --disallowedTools=… --setting-sources=user,project,local
--permission-mode=default --include-partial-messages --await-initialize … --settings "{…}"`. No `--agent`. Its
  `--settings` holds two keys, `fastMode` and `deniedMcpServers`. So the engine reads the project's local settings, and
  the app sets the mode itself, which is why a folder's pick beats the file.
- Its record of each session has `model` and `permissionMode` and no agent field.
- The plugin's `agent`, the lowest settings layer, made the Lead main in every desktop run so far, so nothing the app
  sends overrides the main agent; the project's local settings rank above the plugin's.

So the app should take it, and nothing in what can be seen says otherwise. The one thing not seen is the app's initialize
request over stdin. That makes one new session in the app, after the setup, the first step of Dima's list and a stop: if
the pane or the hall shows no Lead there, v3.8.0 doesn't ship.

## 3.8a: what changed

- `versions/3.json` is the committed template 3, byte for byte. Template 4 adds `"agent": "world-of-agents:lead"` (last,
  so every path writes it in the same place) and drops `Write(~/.world-of-agents/**)`.
- `setup.mjs` manages `agent` beside `permissions` and its env keys. A first setup over an `agent` of the user's own
  stops and names `agent` (never its value); an `agent` that is already the Lead's merges. A version 3 file whose `agent`
  is already the Lead (set by hand, as warning 1 suggests) still counts as version 3. The upgrade lists
  `- removes the deny rule Write(~/.world-of-agents/**)` and `- sets agent to "world-of-agents:lead"`, keeps the user's
  rules after the template's, and "Written." says the Lead applies from the next new session.
- `plugin/settings.json` is gone. `woa` already passed `--agent world-of-agents:lead`, so it is unchanged.
- The guard: a main thread that isn't the Lead was denied Agent, Edit and Write with the Lead's own reasons ("the Lead/PM
  edits BACKLOG.md…"). From v3.8 that is a project whose setup isn't written yet, which is where every project lands
  right after the update from v3.7.0, so it gets its own reason naming the setup (`REASONS.main`). Still a deny. This one
  was not in the brief; it follows from it.
- Tests: the template, the history, a first setup beside another agent, the upgrade from 3 with the user's rules, the
  hand-set agent, another agent on a version 3 file, the guard's reason. Nine planted bugs, nine caught.

## Found on the way, not changed

- `bin/woa` exports `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH=1` with the comment "subagents have no Agent tool", from v2.
  Since v3.4 the guild leads start specialists one level down, and the setup writes 2. Under `woa` a specialist likely
  can't start. Not tested; a one-line fix if Dima wants it.
- The pane can't tell a session that isn't the Lead. Only the guard's reason says so, at the first edit or agent start.
  A pane line ("This session isn't the Lead: …") would need the main agent from the engine: a later choice.
