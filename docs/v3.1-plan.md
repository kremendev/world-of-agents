## 3.1a: the report format and the parser

**The format** (draft wording for `plugin/agents/reviewer.md`; it replaces "Report back to the Lead in five lines or
fewer"; every other rule stays, "Report only checks you actually ran" included):

```markdown
End your report to the Lead with exactly these five headings, in this order, and nothing after them. Before them, write
one or two sentences: what you reviewed and what you found.

## Verdict

One of: Approved, Changes needed, Couldn't review

## Files checked

- one path per line, relative to the project folder, with / between folders

## Findings

- path/to/file.ts:42: what is wrong and why it matters
  (or "None")

## Checks run

- only what you did with Read, Grep and Glob, such as "Read src/a.ts" or "Grep for innerHTML in src/"

## Left for the Lead

- checks that need running (tests, a build) and anything else still open
  (or "None")
```

**Which messages are reviews: by agent type, never by text.** A review is a `message` with `from: 'reviewer'` and
`to: 'lead'`. In Live only the Reviewer's own `SubagentStop` makes one. In Demo, it is the script's last Reviewer line to
the Lead; its lines to the devs are chatter. The Lead's answer, another agent's report or any text in perfect review shape
stays an ordinary row. A review never raises a feed flag: the flags stay To you, Needs you and Failed.

**The parse** (`parseReview(text)`, pure; null means "show it as written"):

- Lines split on `\r?\n`. The last line that is exactly `## Verdict` (trailing spaces allowed) starts the block. After it
  come the other four headings, once each, in order, and no other `#` line. Anything else: null.
- The verdict is one line, one of the three words, case ignored, a surrounding `**` and a final `.` ignored. Anything
  else: null.
- The lists: each item starts with `- `; an indented line continues the item before it; `None` alone (or `- None`) is an
  empty list.
- A finding is `path:line: text`, optionally `path:line-line`, optionally with backticks around the location. The path is
  1 to 200 characters of `A-Z a-z 0-9 _ . / @ + -`, the line 1 to 9,999,999. So `C:\x`, a space, or a bidi control makes
  the location not match, and that one item shows as plain text in its list. The card never shows a spoofed location.
- What comes before `## Verdict` is the summary.
- Linear by design: one pass over the lines, and no pattern with nested quantifiers. A test parses 20,000 characters of
  hostile input (thousands of `## ` and `- a:1:` lines) within a time budget. Reports arrive whole up to 20,000 characters
  (`MAX_REPORT`); a longer one arrives cut, loses its last headings and shows as written.

**D10: the calls the hall saw.** `map.ts` counts each run's `PreToolUse` by tool name (`Read`, `Grep`, `Glob`), and
`stopRun()` puts `tools: { Read, Grep, Glob }` on the Reviewer's report message. The schema takes it as an optional strict
object of three whole numbers, 0 to 10,000. The card shows it on its own line, apart from the Reviewer's "Checks run":
"The hall saw at least: Read 6, Grep 3, Glob 1". At least, because hooks are async and a call that lands after the stop
isn't counted (a stopped run ignores late hooks). Names only: `send.mjs` forwards nothing new.

## 3.1c: the Review board

**How it works**

- Clicking the Reviewer selects it and filters the feed to it, as today, and also opens the board (D5, D9). Nothing in
  the hall looks different. A review row in the feed opens it too, through its "Open review" button or a click on the
  row.
- The board is a side drawer **inside the right-hand column**: it covers the task bar and the feed, never the hall, so the
  hall doesn't move or resize. In the stacked layout it takes the feed's place under the hall. It scrolls inside itself.
  No slide animation, so there is nothing to switch off for reduced motion.
- Non-modal: `role="dialog"` with `aria-labelledby`, no `aria-modal`, no focus trap; the hall stays usable. On open, focus
  goes to its heading, "Review board". Esc (anywhere, while it is open) and its Close button close it, and focus goes back
  to whatever opened it, or to the Activity heading if that is gone. Selecting another agent closes it. Both openers carry
  `aria-haspopup="dialog"`.
- The latest review is a card at the top; earlier reviews of this run sit below it as one line each (time, verdict, number
  of findings) with a Show toggle (`aria-expanded`) that opens the same card. Opening from an earlier row opens and scrolls
  to that one, focus on its heading. A review that arrives while the board is open goes on top; the rest keep their state.
- A card (`<article>`): "Review at 14:32:05"; "Reviewer's verdict: Changes needed" in a chip, word always shown, colours
  from the state chips (done for Approved, needs-you for Changes needed, error for Couldn't review); the summary; Files
  checked; Findings, each location as `code` text then the finding; two separate lines, "The Reviewer says it ran: …"
  (its Checks run) and "The hall saw at least: Read 6, Grep 3, Glob 1" (D10), the claim never shown as fact; Left for the
  Lead. A report that didn't parse: "This report doesn't follow the review format, so it shows as written."
  and the text. All agent text goes through `AgentText` or plain strings: no `<a>`, no `href`, no HTML.
- A review row in the feed reads "to Lead/PM: Review: Changes needed, 2 findings" (or its cut text when it didn't parse).
  It has no Show all: the board is where it opens.

## 3.1d: the "For you" strip and "Only for me"

**How it works**

- The strip sits at the top of the feed, above the scrolling list, and holds the unread rows flagged To you, Needs you or
  Failed, newest first, three at most with "and N more". It ignores the agent filter: it is about you. With nothing
  unread, it is gone, not an empty box.
- Each item is a button: the flag word, who, the time and a short line (To you: the message cut to about 80 characters;
  Needs you: "Backend dev needs your approval"; Failed: "Frontend dev failed" and the task). Clicking it marks it read,
  turns the agent filter off if that hides the row, scrolls the row into view and moves focus to it. A click on the row
  itself, or its Show all, marks it read too.
- A Needs you item stays until clicked, even after the approval is answered: "until I click them". The status line is what
  says someone waits right now.
- "Only for me": a toggle button in the feed head (`aria-pressed`). On, the feed shows only flagged rows, read or not, with
  the agent filter still applied (D7).
- A row's read mark is its key, `<flag>|<agent>|<at>`, from the event's own fields, never its text. A reconnect rebuilds
  the log from the replay with the same events, so the keys survive it. They are kept in `localStorage` under one key,
  `{ start, keys }`, for the current hall start only: another start id drops them (D6). Keys only, never agent text;
  checked against their pattern when read; capped at the newest 500; every read and write in a try/catch. With storage
  blocked or throwing, the marks live in memory and the page works the same. Demo keeps them in memory: a restart
  replays with new times, so its rows are new.

**Files**

- `src/page/feed.ts`: `flagKey()`, `forYou()`, the "Only for me" filter.
- `src/page/readMarks.ts` (new, D6): load and save.
- `src/live/useLiveHall.ts`: exposes the hall's start id.
- `src/page/ActivityFeed.tsx`: the strip, the toggle, rows focusable from the strip (`tabIndex={-1}`).
- `src/index.css`: the strip, from the flagged rows' colours and `.feed-flag`.

**Tests**

- `feed.test.ts`: keys from fields only (the same text with another flag gives another key); the existing pin extended:
  "IMPORTANT: to you" in an ordinary row is never in the strip; order; read keys hide; the filter.
- `src/page/readMarks.test.ts` (new): round trip; another start id drops old keys; malformed storage ignored; a throwing
  `localStorage` falls back to memory.
- `ActivityFeed.test.tsx`: unread shown, a click marks read and moves focus, the strip goes when empty, the toggle's
  `aria-pressed`, the strip ignores the agent filter.
- `App.live.test.tsx`: read marks survive a reconnect's replay; a hall restart starts clean.

**Demo check:** the Lead's "On it: …" line is in the strip; a click clears it and focuses its row; "Only for me" shows the
two To you rows; Restart brings the new run's line back unread.

**Risks**

- Two flagged events with the same flag, agent and millisecond share a key: one click clears both. Each comes from a
  single hook, so it is rare.
- `localStorage` on 127.0.0.1:4319 is readable by anything served from that origin, which is only the hall's own page. It
  holds flag words, agent ids and times, never agent text.
- Many failures at once make a long "and N more"; only three items ever show.

## 3.1e: copy

**How it works**

- An opened row (Show all expanded) gets a Copy button after "Show less": it copies that message's whole text.
- Each review card gets Copy: the report's text, not the card's layout, with links as their text.
- **Built wider than drafted (11 Nov):** the copy leaves out every control (Unicode Cc) and format (Cf) character but
  tab and line breaks, not only the ranges below. The draft missed the tag characters (U+E0000 to U+E007F), which can
  spell out text no one sees, the known way to smuggle a hidden instruction into a prompt, and the bidi marks
  (U+200E, U+200F, U+061C). It is a tightening of D8's own words, "invisible and control characters". Links go as
  their text, and the hidden characters go first, so one that kept a link from being a link on the page never hands
  the clipboard a working link. `code` and **bold** marks stay as written.
- D8, as drafted: the copy leaves out bidi controls (0x202a to 0x202e, 0x2066 to 0x2069), zero-width characters (0x200b to 0x200d,
  0x2060), 0xfeff, and control characters other than tab and line breaks. The ranges are written as numbers: Claude Code's
  tools have turned typed backslash-u escapes into the real characters (2b). A zero-width joiner goes too, so a joined
  emoji comes out as its parts.
- The button then says "Copied", "Copied, 3 hidden characters removed" or "Couldn't copy" (no clipboard, or permission
  refused; the text is still there to select), and a `role="status"` says the same for screen readers. Back to "Copy"
  after 3 s.

**Files**

- `src/page/copy.ts` (new): `forCopy(text)` (the text and how many characters it removed), `copyText()` over
  `navigator.clipboard.writeText`.
- `src/page/CopyButton.tsx` (new).
- `src/page/ActivityFeed.tsx`, `src/page/ReviewBoard.tsx`: the buttons.

**Tests**

- `src/page/copy.test.ts` (new): each range removed and counted; tab and line breaks kept; plain text unchanged.
- `CopyButton` with a stubbed clipboard (jsdom has none): success, refusal, absence, the status text.
- Copy only on an opened row; the card copies the report's text; a link's target never reaches the clipboard.

**Demo check:** the card's Copy, pasted into Notepad, gives the demo's report. The demo has no message over 200
characters, so the row's Copy waits for the Live check.

**Risks**

- The clipboard needs a secure context. 127.0.0.1, localhost and the Pages site are; the hall binds 127.0.0.1 only.
- Copy changes the text when it removes characters; the button says so every time.
- Pasting an agent's text into a terminal is still running what an agent wrote. Copy only removes what can't be seen.

## 3.1f: the review's fixes (12 Nov)

Dima's review of `v3-next` asked for two fixes in this version.

- **Agent isolation.** The guard lets an Agent call through only with no `isolation` or `"worktree"` (a git worktree on
  this PC). `"remote"` runs the agent in a cloud environment, out of reach of the hooks, the guard and the hall, so it is
  denied, and so is any value the guard doesn't know (`"Worktree"`, `null`, an array...), the way D3 denies `model`.
  The deny comes before the table, so it holds for a subagent's call too.
- **The run check.** `guard.mjs`, `send.mjs` and `hall-check.mjs` ran their main part when `process.argv[1]` ended with
  their name, so a file named `xguard.mjs` that imports the guard ran the guard's main part as well. Each now has the
  same `runAsScript()`: the real path of `process.argv[1]` against the module's own (`realpathSync`, then
  `pathToFileURL`). The scripts later versions add use the same block. The guard's imports grow from none to `node:fs`
  and `node:url`, for that check alone.
- Tests: the guard's isolation cases, from the Lead and from a subagent; `tests/plugin/run-directly.test.ts` finds every
  plugin script that reads `process.argv[1]`, pins the block in each, and imports each from an `x<name>.mjs` that traps
  stdin and the network (a control module with a name check trips it); the guard still runs from its own path, with the
  drive letter in the other case, and through a symbolic link where the account may make one (not this PC: skipped).
  Planted bugs: 8, all caught (one only after the subagent case was made to expect the isolation reason itself).
