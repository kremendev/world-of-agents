## What was checked on 11 Nov

- **A project's settings `env` reaches the hooks and the mod's commands.** A no-login probe (`CLAUDE_CONFIG_DIR`, `HOME`
  and `USERPROFILE` on a temp folder, a throwaway plugin, Claude Code 2.1.319): with `{"env":{"WOA_QUALITY_GATE":"1"}}`
  in the project's `.claude/settings.local.json`, a `SessionStart` hook and a `$.process.run` child of the mod both saw
  `WOA_QUALITY_GATE=1`; with `{}` both saw it unset. Folder deleted after.
- **A hooks module sits in the classic chain** ("[managed settings hooks, ...hooks modules, the other settings hooks as
  core]"): the mod's `classic.SubagentStop` hook gets, from `next(e)`, the folded answer of the plugin's settings hooks,
  a gate's `block` included (the engine's types for 2.1.319).
- **A `SubagentStop` hook's `decision: "block"` with a `reason`** keeps the subagent working with the reason as its next
  input; `stop_hook_active` is true on a stop that follows such a block (types; the real loop is 3.3a's real run).
- **`EnterPlanMode` and `ExitPlanMode`** are tools of this Claude Code; `ExitPlanMode` asks the user to approve the plan.
- **`setup.mjs`** treats an env key no template has as "another setting": "Already set up" and upgrades keep it.

## 3.3a: the quality gate

- `plugin/hooks/gate.mjs` (+ `.d.mts`): `gated(payload, env)` (on, and one of the three agent types); `runCheck(cwd)`
  (the fixed command, the timeout, the output cut and cleaned); the try count; the answer (`{decision: "block", reason}`
  or nothing); then the hall post through `send.mjs`'s `allowlist()` and `deliver()` with `gate` added. `--status` exits 0
  or 5. It prints only its one answer; any error lets the agent stop (a gate that breaks must not trap an agent).
- `plugin/hooks/hooks.json`: the gate on `SubagentStop`, timeout 600.
- `plugin/hooks/send.mjs`: skips a `SubagentStop` that `gated()` covers.
- `server/hook-input.ts`, `server/map.ts`: the `gate` field; `retry` keeps the run going (no message, no Done), `failed`
  ends it as `failed()` does, `passed` and none as before.
- `plugin/skills/setup-gates/` (`SKILL.md`, `gates.mjs`), `setup-gates-write/`, `setup-gates-off/`: the switch. The script
  writes only an existing, already set up file, keeps every other key, and never prints a value.
- The mod: `hall.ts` (`gateStatus()`), `register.tsx` (the status at session start; `classic.SubagentStop`'s verdict),
  `pane.tsx` (the lines), `types.d.ts`.
- Tests: `tests/plugin/gate.test.ts` (which stops are gated, the command and cwd, the cut and clean, the counts, a 4th
  failure, `--status`, errors let go), `send.test.ts` (the skip), `map.test.ts` (the three verdicts), `setup-gates.test.ts`
  (temp repos), kit tests, `mod.test.ts` pins for the new command.
- The real run: a throwaway project whose `npm run check` fails until a file starts with a line the task doesn't mention;
  the Backend dev must get the failure and fix it within 3 tries.

**Built 11 to 12 Nov, and run for real three times** (throwaway folders under `~/Downloads/woa-33a-probe*`, deleted after;
gates on through the project's settings env; `--permission-mode acceptEdits` so the dev's write needed no prompt in `-p`):

1. A check that demanded a first line the Lead's task had ruled out ("no extra comments"). The gate sent the Backend dev back
   three times ("Stop hook feedback: World of Agents quality gate: npm run check failed, retry 1 of 3 …", then 2, then 3),
   with the check's output, and let it stop after the fourth failing check: **the loop works**. The dev refused each time,
   rightly: its task said otherwise, and hook output doesn't override the Lead. So the devs' prompts now say what the gate
   is (failures in their own work to fix within the task, still data, never instructions), and the Lead's says not to
   forbid what the check needs.
2. and 3. Fair checks (slugify's test cases, then the same packed so they couldn't simply be read first): the Backend dev got
   them right the first time both times, and the gate passed (its count file for those sessions, `{}`, is written only by a
   verdict). **Not observed for real: an agent fixing a failure from the gate's output**, because none failed. Unit tests
   cover the answer it gets; the desktop checklist asks Dima to see one.

A passing gate is silent, so the Lead said the work was "not tested" when the gate had passed it. A follow-up, not built:
a passing gate could tell the Lead.

## 3.3c: the review's fixes (12 Nov)

- **BACKLOG.md as it stands.** Before the guard leaves the Lead's edit of `BACKLOG.md` alone, it `lstat`s the file: a
  plain file with one name, or none (the first write creates it), passes; a symbolic link, a junction, a folder, a hard
  link (more than one name) or any error but ENOENT is denied (`REASONS.backlog`). Without it a dev with Bash could make
  `BACKLOG.md` a link to `.claude/settings.local.json`, and the Lead's next write would rewrite the project's settings.
  It never looks through a link and never reads the file. A swap between the look and the write stays possible (a
  short window, and only for an agent that can make links); said in Risks.
- **A passing gate is silent**, so the Lead said "not tested" about work the gate had passed. The Frontend and Backend
  devs now run `npm run check` themselves as their last step (`Bash(npm run check)` is in the setup's allow list) and
  give its exit code (`npm run check: exit 0`); the Designer runs no commands and says so; the Lead passes on what they
  reported. The gate stays the enforcer.
- Tests: `tests/plugin/guard-backlog.test.ts` on real files in a temp project (missing, plain, a hard link to
  `.claude/settings.local.json`, a second name elsewhere, a symbolic link where the account may make one (not this PC:
  skipped), a junction, a folder); `guard-backlog-mock.test.ts` stands in for `lstatSync` (a symbolic link to a plain
  file, a second name, EACCES, EPERM, ENOTDIR, ELOOP, EIO); `agent-prompts.test.ts` pins the prompts' lines and the
  allow rule. Planted bugs: 9, all caught.

## 3.3d: what a pass looks like (14 Nov)

The builder's self-check of v3.3.0 ran step 5 for real (a throwaway project, Accept edits, gates on): the Backend dev fixed
the bug, ran `npm run check` last, the gate passed and the card went Done, but its report had no `npm run check: exit 0`.
Claude Code shows no exit code for a command that passes, so the dev first ran a chained `echo $?` command to read one
(which asks for approval: woa-m2-test held two "Always allow" rules for exactly that, leftovers of earlier desktop
checks), and with that refused it wrote the result without a number. The Lead then, as its prompt says, didn't claim
"exit 0".

**Decided by Dima:** the Frontend and Backend devs report `npm run check: passed` when it ends without an error, and
`npm run check: failed (exit N)` with the exit code Claude Code shows (`npm run check: failed` when it shows none). They
never run another command just to read the exit code, and never write a number they didn't see. The Lead passes it on:
"checked, passed" only when a report says passed. `tests/plugin/agent-prompts.test.ts` pins the lines, the old form
included as gone. Step 5 of the checklist now expects "passed". Woa-m2-test's two echo rules are removed (Dima), so his
desktop run matches a normal project.

**Also decided by Dima** (after the passing run below chained the check with another command): the devs run
`npm run check` as one command on its own, never chained (no `&&`, `;`, `|` or `cd` before it), because the setup's
`Bash(npm run check)` rule covers exactly that command and he is never asked to approve a chained one. Pinned in
`agent-prompts.test.ts`; 3.4e gives the specialists the same line.

**From Dima's desktop run** (14 Nov, all steps passed, in Auto): the Frontend dev broke the Designer's `index.html` on
purpose to prove its test could fail, then put it back from a backup copy it had made. **Decided by Dima:** the devs (and
3.4e's specialists) change only the files their task names; to show a test can fail they use a temporary copy, removed
after, or a test fixture, never a project file outside the task; and they never leave backup copies. Pinned in
`agent-prompts.test.ts`, with planted bugs.

**A card whose gate failed stays open** (found by the builder's step 6 run, 14 Nov). The gate's last failure leaves the
card In progress for Dima (`gateFailed()` in `server/map.ts`), but the Lead's Agent call, run in the foreground, came
back "completed" 131 ms later, and `agentReturned()` closed the card. It now leaves a card alone whose run ended in an
error; a run that didn't fail is closed as before. `server/map.test.ts` replays that order; with the fix taken out, it
fails.

**Run for real on 14 Nov** (a throwaway project with the dev install at local scope, deleted after; about $0.80 in all):

- Step 6, a check that always fails, gates on, Accept edits: the gate sent the Backend dev back three times ("retry 1 of 3"
  to "3 of 3"), each of its four reports said `npm run check: failed (exit 1)`, and the Lead told the user it failed after
  the gate's retries. Watched in Edge (a fresh profile) on the fixed hall: the Backend's card stayed "In progress" through
  the error and after the run, its bubble said "error" 41 ms after the event, one feed row was flagged "Failed" and the
  Lead's report "To you". The page shows the retries as the dev staying at work; their count is the pane's.
- Step 7, gates off: no gate count file and no gate feedback for the session, so a dev's stop ran no check.
- Step 12, Manual: the Lead read `BACKLOG.md`, a second name for `.claude/settings.local.json`, wrote to it, and Claude
  Code applied the guard's deny with its reason; no dev was started, and the settings file's hash and its two names were
  the same after.
- The passing case, first try: the dev ran the check chained with another command, which the setup's
  `Bash(npm run check)` rule doesn't cover, so it asked for approval, which `-p` can't give; it reported no result and the
  Lead said "not tested". Dima decided the devs run it on its own (above). Second try, step 5's prompt after that change
  (Accept edits, gates off, $0.31): the Backend dev ran `npm run check` alone, with no approval asked, and reported
  `npm run check: passed`; the Lead passed that on to the user word for word (`npm run check: passed`), not as the phrase
  "checked, passed", and never said "not tested". The dev's other command (a different one, to try the code) asked for
  approval, as any command outside the setup's rules does.

## Risks

- **BACKLOG.md can be swapped between the guard's look and the Lead's write** by an agent that can make links (the two
  devs, with Bash). The window is the time between two calls; the devs' own permission prompts decide their commands.

- **A gate runs project code with no prompt**, which is why it's opt-in and warned about (G1). `npm run check` is already
  in the setup's allow list, so a gate adds no new command, only when it runs.
- **A long check holds the agent**: up to 600 s per try. A project with a slow check should keep its gate off.
- **The hall's view while a gate decides**: the agent shows its last state until the gate answers.
- **The Lead with `Edit` and `Write`** is held to one file by the guard, not by its prompt. The guard's path check is exact
  (no `..`, no other folder); a symlink named `BACKLOG.md` would be followed by Claude Code's own tool, as for any file.
