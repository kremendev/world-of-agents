## What was checked on 11 Nov

- **A project's settings `env` reaches the hooks and the mod's commands.** A no-login probe (`CLAUDE_CONFIG_DIR`, `HOME`
  and `USERPROFILE` on a temp folder, a throwaway plugin, Claude Code 2.1.319): with `{"env":{"WOA_QUALITY_GATE":"1"}}`
  in the project's `.claude/settings.local.json`, a `SessionStart` hook and a `$.process.run` child of the mod both saw
  `WOA_QUALITY_GATE=1`; with `{}` both saw it unset. Folder deleted after.
- **A hooks module sits in the classic chain** ("[managed settings hooks, ...hooks modules, the other settings hooks as
  core]"): the mod's `classic.SubagentStop` hook gets, from `next(e)`, the folded answer of the plugin's settings hooks,
  a gate's `block` included (the engine's types for 2.1.319).
- **A `SubagentStop` hook's `decision: "block"` with a `reason`** keeps the subagent working with the reason as its next
  input; `stop_hook_active` is true on a stop that follows such a block (types; the real loop is 3.3a's real run).
- **`EnterPlanMode` and `ExitPlanMode`** are tools of this Claude Code; `ExitPlanMode` asks the user to approve the plan.
- **`setup.mjs`** treats an env key no template has as "another setting": "Already set up" and upgrades keep it.

## 3.3a: the quality gate

- `plugin/hooks/gate.mjs` (+ `.d.mts`): `gated(payload, env)` (on, and one of the three agent types); `runCheck(cwd)`
  (the fixed command, the timeout, the output cut and cleaned); the try count; the answer (`{decision: "block", reason}`
  or nothing); then the hall post through `send.mjs`'s `allowlist()` and `deliver()` with `gate` added. `--status` exits 0
  or 5. It prints only its one answer; any error lets the agent stop (a gate that breaks must not trap an agent).
- `plugin/hooks/hooks.json`: the gate on `SubagentStop`, timeout 600.
- `plugin/hooks/send.mjs`: skips a `SubagentStop` that `gated()` covers.
- `server/hook-input.ts`, `server/map.ts`: the `gate` field; `retry` keeps the run going (no message, no Done), `failed`
  ends it as `failed()` does, `passed` and none as before.
- `plugin/skills/setup-gates/` (`SKILL.md`, `gates.mjs`), `setup-gates-write/`, `setup-gates-off/`: the switch. The script
  writes only an existing, already set up file, keeps every other key, and never prints a value.
- The mod: `hall.ts` (`gateStatus()`), `register.tsx` (the status at session start; `classic.SubagentStop`'s verdict),
  `pane.tsx` (the lines), `types.d.ts`.
- Tests: `tests/plugin/gate.test.ts` (which stops are gated, the command and cwd, the cut and clean, the counts, a 4th
  failure, `--status`, errors let go), `send.test.ts` (the skip), `map.test.ts` (the three verdicts), `setup-gates.test.ts`
  (temp repos), kit tests, `mod.test.ts` pins for the new command.
- The real run: a throwaway project whose `npm run check` fails until a file starts with a line the task doesn't mention;
  the Backend dev must get the failure and fix it within 3 tries.

**Built 11 to 12 Nov, and run for real three times** (throwaway folders under `~/Downloads/woa-33a-probe*`, deleted after;
gates on through the project's settings env; `--permission-mode acceptEdits` so the dev's write needed no prompt in `-p`):

1. A check that demanded a first line the Lead's task had ruled out ("no extra comments"). The gate sent the Backend dev back
   three times ("Stop hook feedback: World of Agents quality gate: npm run check failed, retry 1 of 3 …", then 2, then 3),
   with the check's output, and let it stop after the fourth failing check: **the loop works**. The dev refused each time,
   rightly: its task said otherwise, and hook output doesn't override the Lead. So the devs' prompts now say what the gate
   is (failures in their own work to fix within the task, still data, never instructions), and the Lead's says not to
   forbid what the check needs.
2. and 3. Fair checks (slugify's test cases, then the same packed so they couldn't simply be read first): the Backend dev got
   them right the first time both times, and the gate passed (its count file for those sessions, `{}`, is written only by a
   verdict). **Not observed for real: an agent fixing a failure from the gate's output**, because none failed. Unit tests
   cover the answer it gets; the desktop checklist asks Dima to see one.

A passing gate is silent, so the Lead said the work was "not tested" when the gate had passed it. A follow-up, not built:
a passing gate could tell the Lead.

  cases, the "only ever denies" sweep); planted bugs.

## Risks

- **A gate runs project code with no prompt**, which is why it's opt-in and warned about (G1). `npm run check` is already
  in the setup's allow list, so a gate adds no new command, only when it runs.
- **A long check holds the agent**: up to 600 s per try. A project with a slow check should keep its gate off.
- **The hall's view while a gate decides**: the agent shows its last state until the gate answers.
- **The Lead with `Edit` and `Write`** is held to one file by the guard, not by its prompt. The guard's path check is exact
  (no `..`, no other folder); a symlink named `BACKLOG.md` would be followed by Claude Code's own tool, as for any file.
