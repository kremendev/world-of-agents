## What was checked on 12 Nov (no model run)

A throwaway folder under `~/Downloads/woa-team-probe` (deleted after), with `CLAUDE_CONFIG_DIR`, `HOME` and `USERPROFILE` on
a temp folder, Claude Code 2.1.319:

- **A folder marketplace works at local scope.** A `marketplace.json` listing `woa-team` at `./team`, then
  `claude plugin marketplace add <folder>` and, in a project, `claude plugin install woa-team@woa-local --scope local`:
  installed, enabled, local.
- **It loads in place.** `claude plugin list` says "Read from: <the folder>\team", not a cache copy. A file added after the
  install (a hooks file) showed in `claude plugin details woa-team` with no reinstall. So a change to the folder applies at
  the next `/reload-plugins`.
- **The namespace is `woa-team:<name>`.** `claude -p --agent woa-team:react-dev` with no login: a `SessionStart` hook saw
  `agent_type=woa-team:react-dev`. A project or user agent can't take that name (Claude Code skips agent files whose name
  holds `:`, checked in 2a), so a cloned repo can't fake a specialist.
- **What that means for safety:** the team folder is a live plugin. Whatever lands in it loads: an agent's prompt, a skill,
  and also a `hooks/` folder (code that runs in every session with the plugin on) or a skill line starting with `` !` ``
  (a shell command Claude Code runs when the skill is used, with no hook seeing it). So nothing but the plugin's own
  generator may write there, it writes only the files it builds, and a skill's text is refused if it holds such a line.

## 3.4a: the team folder

- `plugin/team/defaults.json`: the 8 specialists and their skills (names, roles, guilds, kinds), and the skills' texts in
  `plugin/team/skills/*.md`, written by us.
- `plugin/team/team.mjs` (+ `.d.mts`): `teamSchema` checks (strict, bounded, slugs `[a-z0-9-]`); `buildAgent()` and
  `buildSkill()` make each file from data, the frontmatter by the generator alone; `refused(text)` finds a line starting
  with `` !` ``; `writeTeam(dir, team)` writes only `team.json`, `agents/<id>.md` and `skills/<id>/SKILL.md` (and the two
  manifests), refuses any path outside `dir`, and deletes only files it generated; `init(home)` creates
  `~/.world-of-agents/team` from the defaults when there is none, never over one.
- `plugin/skills/setup-team/` (`SKILL.md`, a fixed injected command, Dima-only) and `setup-team-write/`: the dry run shows
  what it would create and the two commands to install it in a project; the write creates it.
- Tests: `tests/plugin/team.test.ts` (schema, generator, the refusal, paths, no overwrite), `server/setup-team.test.ts`.

**3.4a built 12 Nov.** `plugin/team/team.mjs`, the defaults and their 14 skill texts, `/world-of-agents:setup-team` and
`-write`. Building it found two descriptions with ": " in their YAML (`setup-gates-write`'s and `setup-team`'s): an
unquoted value can't hold one. Both fixed, and a test now checks every skill's and agent's description in the plugin.
The generated prompts carry 3.3c's rule (rebuilt 12 Nov): a specialist that edits and has a shell runs `npm run check`
last and gives its exit code; a design specialist runs no commands and says so. 3.4e (14 Nov) brings that rule in line
with the devs' since 3.3d: `npm run check: passed` when it ends without an error, `npm run check: failed (exit N)` only
with an exit code Claude Code showed, never a command just to read one, and the check run as one command on its own,
never chained, so the setup's rule covers it; and every specialist that edits changes only the files its task names and
leaves no backup copies, as the devs (Dima's v3.3.0 desktop run). `team.test.ts` pins it, the old form as gone.

## 3.4c: the skill buttons, with T8's one-time key

**Built 12 Nov, on Dima's T8.** How the pieces fit:

- **The pane.** "Change skills" (while the hall runs) makes a key: 32 bytes from the engine's `crypto.getRandomValues`,
  base64url. It goes to `node <plugin>/hooks/hall-key.mjs` on stdin only, which checks it is exactly `{"key"}`, does
  send.mjs's handshake and posts it to `POST /api/key` with the token (exit 0 when the hall took it). Then the pane shows
  a second link, `http://localhost:4319/#k=<key>`, for 60 s. The key lives in a module variable of register.tsx for that
  minute, never in `$.state` or `$.store` (a kit test watches every write). The plain "Open hall" link is unchanged.
- **The hall.** `server/keys.ts` keeps digests only, in memory: the newest 10 keys and 5 sessions. `POST /api/session`
  (the page's exact Origin, JSON, 256 bytes) takes a key once: a second try says `used`, one older than 60 s or never
  seen says `expired` (and is spent). It answers 204 with `woa_team=<32 random bytes>; HttpOnly; SameSite=Strict;
Path=/api/team`. `GET /api/team` needs that cookie; `POST /api/team` needs it, the exact Origin, JSON, at most 64 KiB
  and `teamChangeSchema` (add, change or delete a skill; give or take one). One write at a time: `team.mjs`'s
  `applyChange()` (pure; at most 5 skills a specialist, `textProblem()` on the text, `problem()` on the result), then
  `writeTeam()` and `logChange()` (`changes.json` in the team folder, newest 50, time, kind and names only). Its errors are
  team.mjs's own fixed words. It starts nothing.
- **The page.** `main.tsx` calls `startTeamSession()` before React renders (StrictMode runs effects twice, and a key works
  once): any `#k=` leaves the address bar through `history.replaceState` first, then the key goes to `/api/session` in
  the body. The Team panel (a header button in Live, or open at once after a key) takes the review board's place over
  the right-hand column. It lists specialists and skills as text; New skill and Change open a form whose Preview shows
  the whole text line by line, flags links and command-like lines, and names every refusal (the schema's field rules,
  a line starting with `` !` ``, invisible characters, empty, too long); Save is off while any stands, and any edit after
  the preview hides it, so what is saved is what was previewed. Delete asks first and says how many specialists lose it.
- **The pane's change lines.** `hooks/team-log.mjs` prints `{"changes": [...]}`, the newest 20 entries that pass
  `isChange()`; the mod keeps the newest five only when every entry is exactly one (`changesOf()`), and shows
  "12 Nov 14:05 Skill added: Release notes". It runs while the hall runs: at session start, after the Lead's turns, and
  every 20 s for ten minutes after a key, so a change shows within 20 s while Dima edits. That is the mod's third
  kept child output, as T8 asked for a line per change.
- **Tests.** `server/team-api.test.ts` (16: every control on every route, one-time and 60 s, cookie flags, the files a
  write touches, refusals that write nothing, two writes at once), `tests/plugin/hall-key.test.ts` (the key only after the
  handshake, never to a program without the token; the log's strictness), `src/team/team-page.test.ts` (the address bar
  cleared before the hall is asked; the schema and team.mjs agree on names), `src/page/TeamPanel.test.tsx` (11), the kit
  (the key on stdin only and nowhere kept, the link for 60 s, a new key each press, change lines, seven bad logs dropped),
  `mod.test.ts` (two links, the key's source, the new commands, stdin and stdout lines), `App.live.test.tsx` (the Team
  button, the column inert under it, Esc, a used key's line). Planted bugs: 22, all caught. Two needed a second look: the
  size cap test built its body from the constant it tested (fixed: a fixed size), and the first expiry plant left the
  view's own reset in place, so it wasn't a bug (planted again as the timer's removal). A plant on the preview's compare
  changed nothing, because any edit already hides the preview: two layers, not counted.

## 3.4f: after the self-check (14 Nov)

Dima's decisions on the builder's self-check of v3.4.0, where three small real runs never saw a specialist start (the
Frontend dev kept the work as small, the Lead left "the React dev" out of its hand-off, and once the Lead refused, since
only guild leads start specialists), and agent memory clashed with the guard.

- **The Designer changes only the files its task names**, as the devs and the specialists that edit: a temporary copy
  (removed when done) or a fixture to show a test can fail, never backup copies.
- **Specialists on request.** The Lead knows the guilds and passes a request for a specialist on in the hand-off to its
  guild lead, naming the specialist; it never starts one itself. A guild lead hands work to a specialist when the user
  asked for one (the Lead's hand-off says so), or when a piece is clearly in a specialist's area and more than a small
  change (for the Reviewer, a small check); small ones it does itself.
- **The Lead's `Agent` is bare** (Dima's choice after the real run below). The run showed why no specialist ever
  started: the Lead's `Agent(designer, frontend, backend, reviewer)` becomes the whole session's `allowedAgentTypes`
  in Claude Code 2.1.319, and nested agents inherit it. The Frontend dev's agent list held exactly those four (no
  specialist, no built-in), and the engine answers a call outside it with "Agent type … not found" (read in its code).
  The guard, deny-only and fail-closed, is now the one check: the Lead the four, each guild lead its own specialists.
  The Lead and the guild leads see every agent type in their lists, and the guard denies the rest. With hooks turned
  off (`disableAllHooks`) nothing limits the Lead: the price of this choice. A second layer was looked for at Dima's
  ask (a list with patterns, such as `Agent(world-of-agents:*, woa-team:*)`): Claude Code 2.1.319 has none. Its
  listing filter and its spawn check both compare exact names (`allowedAgentTypes.includes(type)`, read in its code),
  so such a list would match no agent and the Lead could start nobody. The bare `Agent` stays.
- **Exactly `npm run check`, nothing added** (Dima, after the real run below): the devs and every specialist with a
  shell run it as written, with no `--prefix`, no path and no flags, as well as never chained, because the setup allows
  exactly that command. The Designer and the design specialists have no shell and run nothing, so they say so, as before.
- **Agent memory is off** for every agent: no `memory` in any agent file, the specialists' included. With
  `memory: local` the Lead's and the Reviewer's notes were always denied by the guard, under the backlog's reason, and
  each editing guild lead's asked for approval every time in Manual; memory also gave the Reviewer Write and Edit, which
  its file doesn't list. The guard now denies an Edit or Write into all three places Claude Code keeps agent memory,
  `.claude/agent-memory-local`, `.claude/agent-memory` or `~/.claude/agent-memory` (a `.claude` folder, then one of the two names), for every caller, with
  its own reason: "agent memory is off". By the path as written (`.` and `..` resolved, case-blind on Windows);
  nothing loads from those folders now, so the rule is for a true reason, not a lock. A `CLAUDE_CONFIG_DIR` elsewhere
  moves the user's folder out of its reach.
- Tests: `agent-prompts.test.ts` (the Designer's rule, the Lead's pass-on, each guild lead's hand-over, nothing added
  to the check, no `memory` in any agent file), `team.test.ts` (no `memory` in a specialist, nothing added to the
  check), `guard.test.ts` (every caller in each of the three folders, five ways in, seven look-alikes), `roster.test.ts`
  (every agent has a bare `Agent`; the guard's main row is the other four). Planted bugs: 27, all caught.

**The real runs (14 Nov).** A throwaway project with woa-m2-test's files and a throwaway home with the team, in Accept

## Risks

- **The editor's link is briefly visible in the browser's command line** when the desktop app opens it (and stays in a
  browser process started for it, until that closes). It works once and for 60 s, so a reader after the exchange gets
  nothing; the README says so.
- **Anything that can read `~/.world-of-agents/token` can mint a key**, as it can post hooks. It could also write the
  team folder directly; the guard's folder rules and the template's denies keep agents away from it (best effort for
  shell commands).

- **No agent starts until the team exists** (T4, T10): the price of failing closed.
- **The team folder is a plugin**: anything written there runs or instructs. The generator writes only its own files.
- **Best effort only** for the shell rule, as for `.env`: a command that builds the path another way gets past it.
