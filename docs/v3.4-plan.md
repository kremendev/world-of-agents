## What was checked on 12 Nov (no model run)

A throwaway folder under `~/Downloads/woa-team-probe` (deleted after), with `CLAUDE_CONFIG_DIR`, `HOME` and `USERPROFILE` on
a temp folder, Claude Code 2.1.319:

- **A folder marketplace works at local scope.** A `marketplace.json` listing `woa-team` at `./team`, then
  `claude plugin marketplace add <folder>` and, in a project, `claude plugin install woa-team@woa-local --scope local`:
  installed, enabled, local.
- **It loads in place.** `claude plugin list` says "Read from: <the folder>\team", not a cache copy. A file added after the
  install (a hooks file) showed in `claude plugin details woa-team` with no reinstall. So a change to the folder applies at
  the next `/reload-plugins`.
- **The namespace is `woa-team:<name>`.** `claude -p --agent woa-team:react-dev` with no login: a `SessionStart` hook saw
  `agent_type=woa-team:react-dev`. A project or user agent can't take that name (Claude Code skips agent files whose name
  holds `:`, checked in 2a), so a cloned repo can't fake a specialist.
- **What that means for safety:** the team folder is a live plugin. Whatever lands in it loads: an agent's prompt, a skill,
  and also a `hooks/` folder (code that runs in every session with the plugin on) or a skill line starting with `` !` ``
  (a shell command Claude Code runs when the skill is used, with no hook seeing it). So nothing but the plugin's own
  generator may write there, it writes only the files it builds, and a skill's text is refused if it holds such a line.

## 3.4a: the team folder

- `plugin/team/defaults.json`: the 8 specialists and their skills (names, roles, guilds, kinds), and the skills' texts in
  `plugin/team/skills/*.md`, written by us.
- `plugin/team/team.mjs` (+ `.d.mts`): `teamSchema` checks (strict, bounded, slugs `[a-z0-9-]`); `buildAgent()` and
  `buildSkill()` make each file from data, the frontmatter by the generator alone; `refused(text)` finds a line starting
  with `` !` ``; `writeTeam(dir, team)` writes only `team.json`, `agents/<id>.md` and `skills/<id>/SKILL.md` (and the two
  manifests), refuses any path outside `dir`, and deletes only files it generated; `init(home)` creates
  `~/.world-of-agents/team` from the defaults when there is none, never over one.
- `plugin/skills/setup-team/` (`SKILL.md`, a fixed injected command, Dima-only) and `setup-team-write/`: the dry run shows
  what it would create and the two commands to install it in a project; the write creates it.
- Tests: `tests/plugin/team.test.ts` (schema, generator, the refusal, paths, no overwrite), `server/setup-team.test.ts`.

**3.4a built 12 Nov.** `plugin/team/team.mjs`, the defaults and their 14 skill texts, `/world-of-agents:setup-team` and
`-write`. Building it found two descriptions with ": " in their YAML (`setup-gates-write`'s and `setup-team`'s): an
unquoted value can't hold one. Both fixed, and a test now checks every skill's and agent's description in the plugin.
The generated prompts carry 3.3c's rule (rebuilt 12 Nov): a specialist that edits and has a shell runs `npm run check`
last and gives its exit code; a design specialist runs no commands and says so.

## 3.4b: the guard, the template, the guild leads

- `plugin/hooks/guard.mjs`: reads `~/.world-of-agents/team/team.json` (the one file it reads; `node:fs`, `node:os` and
  `node:path` its only imports); builds `MAY_START.subagents` from it; missing or broken: every agent start denied with a
  reason naming `/world-of-agents:setup-team`. `checkEdit()` adds the team's editing specialists. The shell rule adds
  `.world-of-agents`. `decide(raw, table)` takes the table, so tests need no home folder.
- `plugin/skills/setup-project/template.json`: version 2 (the committed one saved as `versions/2.json` first) adds the
  three denies on `~/.world-of-agents/**`; the upgrade path applies.
- `plugin/agents/{designer,frontend,backend,reviewer}.md`: the `Agent` tool, and how to hand focused work to their
  specialists; `memory: local` for them and the Lead. `src/office/roster.ts` and `roster.test.ts` follow.
- Tests: `guard.test.ts` (the table rows, a missing and a broken file, the shell rule), `setup-skill.test.ts` (version 2 and
  the upgrade), `roster.test.ts`.

**3.4b built 12 Nov.** The template's new version is 3 (the committed one, with the PowerShell push deny, is saved as
`versions/2.json`, byte for byte); a test upgrades a version 2 file and sees exactly the three new denies added. The guard
reads the table through `team.mjs`'s `readTeam()`, so its own code still opens no file; its one import is that module.

**The review's fix (12 Nov, folded into 3.4b).** The guard denies `Edit` and `Write` whose `file_path` is in
`~/.world-of-agents`, for every caller, whether or not the project ran the setup: the template's denies apply only where
the setup wrote them, and the team folder is a live plugin. `inWoaFolder()` checks the path twice, case-blind on
Windows: as written (a leading `~` is home, `.` and `..` resolved against the call's cwd, a `\\?\` prefix dropped) and
where it really lands, through `realpathSync.native` on the deepest part that exists. The second check was not in the
review's words: it closes a junction or link in the project that leads into the folder, and 8.3 short names, which this
PC keeps (`.world-of-agents` is also `WORLD-~1`; a test made one and the guard denied it). Any error but ENOENT and
ENOTDIR while resolving denies the call. `tests/plugin/guard-woa-folder.test.ts`: every caller, eleven ways in, the
junction, the short name, a look-alike folder left alone, a home with no folder yet; planted bugs: 8, all caught.
The guard's imports grow to `node:fs`, `node:os`, `node:path`, `node:url` and `team.mjs`.

## Risks

- **No agent starts until the team exists** (T4, T10): the price of failing closed.
- **The team folder is a plugin**: anything written there runs or instructs. The generator writes only its own files.
- **Best effort only** for the shell rule, as for `.env`: a command that builds the path another way gets past it.
