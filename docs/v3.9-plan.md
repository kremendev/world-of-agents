# v3.9.0: a team per project, one skill library for the PC

Plan only, from Dima's brief of 16 Nov ("PLAN, DON'T BUILD", part A), with his answers of the same day worked in.
Nothing here is built, and nothing is until he sends the approved Team page mockup, which A and B share; Claude makes it
in his review chat. This plan says what the page must let him do, never how it looks.

**In one line:** every project gets its own team under `~/.world-of-agents/projects/<key>/`, loaded through its own
registered marketplace, while every skill on the PC lives once in `~/.world-of-agents/library/`. New projects start
empty; the 8 current specialists become a one-click starter team; nothing Dima has today is lost.

B (adding skills from outside, v3.10.0) builds on this library, so A comes first. They are two versions on purpose: A
moves where things live; B opens the first door to the network. Each gets its own review.

## What Dima asked (16 Nov)

- Every new project starts with no specialists and no skills; he adds what that project needs. Flexible.
- The library: every skill on this PC, in one place. Each project's team picks from it.
- The 8 current specialists become an optional starter team, added with one click, or he copies another project's team.
- Security: a project's team lives under `~/.world-of-agents`, never in the project folder, so a cloned repo can never
  bring its own team or specialists. The guard finds the team of the session's project. An empty team is valid: the
  guild leads work and no specialist starts. No team at all: deny as today, naming the setup.
- Probe how the local `woa-team` plugin works per project (marketplaces, local scope, agent names) and how the guard
  finds the project.
- Migration: his current team and skills, and the projects already set up, keep what they have.

## What the probes already settled (16 Nov, Claude Code 2.1.325, no login)

1. **One registered marketplace per project works, and agent names don't change.** Two folder marketplaces, `woa-p1` and
   `woa-p2`, each holding a plugin named `woa-team` with a different specialist, each installed at local scope in its
   own project: project 1's session listed only `woa-team:frontend-alpha`, project 2's only `woa-team:frontend-beta`.
   So the guard's `woa-team:` prefix, the guild leads' prompts and the hall's `specialist` event stay as they are.
2. **A marketplace a project declares in its own settings is ignored.** `extraKnownMarketplaces` in a project's
   `settings.local.json`, pointing at a folder, without `claude plugin marketplace add`: "Skipping orphaned enabledPlugins
   entry woa-team@woa-here: marketplace not registered", and no agent loaded. Good: a cloned repo can't bring a
   marketplace of its own this way. (Interactive sessions may offer to add a project's marketplace; that offer is for
   `.claude/settings.json`, and it still needs Dima's yes.)
3. **`marketplace add` writes the marketplace into the user settings** ("declared in user settings"). One per project
   means that list grows by one per project; removing a project removes its line (see Limits).
4. **Hooks get `CLAUDE_PROJECT_DIR`**: the session's project folder, forward slashes (`C:/Users/…/proj`), next to a `cwd`
   with backslashes. Seen in `SessionStart` only so far (the spike below covers the rest).
5. **The pane can know its project:** the mods API has `$.session.cwd()`, "the directory the session runs in, absolute".

## The design

### Where things live

```
~/.world-of-agents/
  library/                      every skill on this PC (data, not a plugin)
    library.json                ids, names, descriptions, source, ref, license, dates (strict schema, as team.json)
    skills/<id>.md              each skill's text, exactly as approved
  projects/<key>/               one per project, a folder marketplace named woa-<key>
    .claude-plugin/marketplace.json   { name: "woa-<key>", plugins: [{ name: "woa-team", source: "./team" }] }
    project.json                the project's folder as it was set up, and its display name
    team/                       the woa-team plugin, generated, loaded in place
      team.json                 version 3: specialists, the library skills picked, preset, on, generator
      agents/*.md, skills/*/SKILL.md   generated by team.mjs from team.json and the library's texts
      notes.json, changes.json  notes and the change log, per project now
  team/                         the shared team of v3.4 to v3.8, kept as an unused backup: only the one-time copy reads it
  token                         the hall's, as today
```

- **The key** is the project folder's real path, normalised (Windows: case-folded, backslashes), hashed (SHA-256), as
  `<folder name, kebab-case, at most 24 chars>-<first 10 hex>`: `agent-office-3f2a91c07d`. Readable in
  `claude plugin list`, unique, and nothing a repo can choose: it comes from where Dima put the folder.
- **Skills by reference.** A project's team names library skill ids; team.mjs writes each picked skill's `SKILL.md` from
  the library's text. Changing a skill in the library rewrites it in every project that uses it (and the pane's line says
  how many). A project never holds a skill the library doesn't.
- **The library holds skills only; specialists live per project** (Dima). Reuse comes from the starter team (the 8
  defaults) and from copying another project's team.
- **Notes are per project** (Dima). A note is a fact about one project ("the counter's code lives in src/"); today they
  are shared by every project, which is wrong for most notes. Copying another project's team copies no notes, and the
  starter team has none. The shared team's notes are offered for review once per project, at its copy (Migration).

### How a session finds its team

- **The guard** reads `CLAUDE_PROJECT_DIR`, never the hook input's `cwd`: `cwd` follows the Bash tool's `cd`, so an agent
  could move it into another project's folder. Real path, normalised, hashed: the key. Then
  `projects/<key>/team/team.json` through the strict schema.
  - Found and valid, even with no specialists: the guild leads' rows come from it, as today. An empty team is valid.
  - Not found: the project has no team of its own yet. The Lead may still start the guild leads (its row is fixed, never
    from a team), and every specialist start is denied with its own reason, naming the step: "This project has no team
    of its own yet: type /world-of-agents:setup-team-write here, or press Give this project its own team in the pane."
    One source only (Dima: two sources for the guard is one too many): the guard never reads the shared folder.
  - No World of Agents team setup on the PC at all (no `library/`, no `projects/` and no shared `team/`): every agent
    start denied, naming `/world-of-agents:setup-team`, as today. That is how "no team at all: deny as today" and "the
    guild leads keep working" fit together: the first is a PC never set up, the second a project not moved yet. The
    shared folder counts here only by being there, so Dima's guild leads keep working right after the update, before his
    first v3.9 setup; its team is never read for rows.
  - `CLAUDE_PROJECT_DIR` missing or not a folder: denied, its own reason. Fail closed, as everything in the guard.
  - A cloned repo's `.claude/settings.json` that enables `woa-team@woa-<another key>` loads that project's agent files,
    but the guard reads this project's team, so none of them can start. A test pins it.
- **The pane** gives the hall its project with the editor's key: hall-key.mjs's stdin becomes `{ key, project }`, from
  `$.session.cwd()`. The hall binds the session cookie to that project and edits only its team. A project the hall has
  no team for opens the empty state, from which the setup is the way in (the hall creates no project on its own).
- **The setup** (`/world-of-agents:setup-team`, then `-write`) in a project creates `projects/<key>/` with an empty team
  and prints the two commands Dima runs once (Claude Code has no way for a skill to register a marketplace):
  `claude plugin marketplace add ~/.world-of-agents/projects/<key>` and
  `claude plugin install woa-team@woa-<key> --scope local`.

### The Team page (needs the mockup first)

What it must let Dima do; the mockup decides the look:

1. See whose team it is: the project's name and folder, always visible.
2. An empty project: "No specialists yet", with **Add the starter team** (one click; lists the 8 and their skills
   before it adds them), **Copy from another project** and **+ Add specialist**.
3. **Copy from another project:** a list of the PC's projects (name, folder, how many specialists), a preview of what
   comes (specialists with their skills, never notes), then copy. Copies, never links: the two teams change apart
   afterwards.
4. **The library:** every skill on the PC, which projects use each, add a skill to this project or to a specialist,
   remove one from the library (asks first, names the projects that lose it).
5. A project with no team of its own yet: a banner saying its specialists can't start, with **Give this project its own
   team** (a copy of the shared team, or empty). The pane's button of the same name opens the page right here.
6. **The shared notes, after a copy:** each old shared note waiting for review in this project's Notes tab, with **Keep**
   or **Drop**, one at a time; nothing kept until he says so.

### Migration: nothing is lost

Dima's answers (16 Nov): no permanent fallback; a one-time copy per project, on his command; the old shared folder kept
as an unused backup.

1. The first v3.9.0 setup (`/world-of-agents:setup-team-write`) builds the library from the shared team's skills: the
   same ids, the texts byte for byte, source "your team (v3.7)". The shared folder stays where it is, untouched.
2. **Until a project is moved,** its guild leads keep working and its specialist starts are denied with the reason that
   names the step (above). Its sessions may still load `woa-team@woa-local`'s files; the guard never reads that team.
3. **The move, once per project, on his command:** `/world-of-agents:setup-team-write` in the project, or **Give this
   project its own team** in the pane. It copies the shared team's specialists, skill picks and switches, or starts
   empty, and prints the swap: `claude plugin uninstall woa-team@woa-local --scope local`, then the two commands above.
4. **Notes are never copied silently.** After the copy, the shared team's notes wait in that project's Notes tab, each
   kept or dropped by Dima. Moving a second project offers them again there, each decided again, never carried over from
   the first project's choices.
5. **The shared folder stays as a backup.** Nothing reads it after the copies, nothing deletes it.

### Limits

At most 100 projects and 200 library skills; 64 skill picks per project and 5 specialists per guild, as today. Removing a
project (Team page, asks first) deletes `projects/<key>/` and prints the two commands that unregister it; a project
folder that no longer exists is flagged, never removed on its own.

## Security

- Every team and the library are under `~/.world-of-agents`, which the guard (Edit and Write, as written and as resolved,
  for every caller) and the template's `Read` and `Edit` denies already keep agents out of. Nothing new in a project
  folder.
- The project comes from `CLAUDE_PROJECT_DIR`, set by Claude Code, never from the model's `cwd`, a file or the page.
- The hall's team API takes a project only through the key's exchange; a request can't name another project.
- team.mjs stays the only writer, now of `library/` and `projects/` too; its schema gets `project.json` and
  `library.json`, both strict, every value quoted in frontmatter as since 3.6e.

## 3.9a: the probes (16 Nov, Claude Code 2.1.325)

The Team page mockup was approved the same day (Dima, in his review chat); this version builds to it.

1. **`CLAUDE_PROJECT_DIR` is the project folder for every caller.** A throwaway plugin logged every `PreToolUse` in a
   tiny Haiku run ($0.007): the main thread's Bash and Agent calls, a subagent's Read and its own Agent call, and an
   agent started with `isolation: "worktree"` all saw the project folder. That last one's hook `cwd` was
   `proj\.claude\worktrees\agent-…`, so the hook's `cwd` would have sent a worktree agent to no team; the variable didn't.
   A `cd ..` by the main thread didn't move anything: Claude Code reset the shell to the project folder. The variable
   came with backslashes in this run and with forward slashes in v3.8's probe, so the key normalises both. It was never
   missing, so a missing one is treated as "no team of its own" rather than a reason of its own.
2. **`$.session.cwd()` is the same folder** (a throwaway mod at session start, no login). The mod's processes don't get
   `CLAUDE_PROJECT_DIR`, so the pane passes the folder on their stdin (the engine's option is `stdin`).
3. and 4. Twenty registered marketplaces and the swap from `woa-team@woa-local`: in the self-check, with the real files.
   The desktop app's side is Dima's list.
